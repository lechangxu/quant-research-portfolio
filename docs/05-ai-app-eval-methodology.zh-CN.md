# 05 — AI 应用质检方法论：从生产判官链长出来的通用体系

**论点。** AI 落地最后一公里最稀缺的能力不是 prompting、不是 RAG 调优，是**评估工程**（evaluation engineering）：建一套系统来判定「这个 AI 输出敢不敢上线」，并且在模型和应用都在漂移的情况下保持这套系统自身的诚实。多数团队有 demo，极少数团队有**判决流水线**。

**证据基础。** 我有一套跑了两个月的生产评估 harness，用于验收 AI 生成的代码改动：三层判官链（J1/J2/J3，带独立性约束）、golden set 校准、逃逸库、metrics 回写判据。它长在**代码域**。本文是它的泛化：事故教给我的东西，重述成适用于任何 AI 应用的方法论 —— 以及我在客户现场头两周会怎么做。

每一条都锚着一次真事故。[English version](05-ai-app-eval-methodology.md)

## 1. 三层判定器栈

压倒一切的教训：**没有任何单一层能覆盖整个失败空间。** 有效的栈：

| 层 | 判定什么 | 我 harness 里的实例 |
|---|---|---|
| **确定性校验** | 精确条件 —— 机器可判、零自由裁量 | L0 机器判据：文件存在、命令输出匹配、schema 对账 |
| **LLM 判官** | 稳定语义标准 —— 跨运行一致 judgment | L2 独立评审：diff 是否真的实现了卡面 |
| **人审** | 模糊或高后果决策 | L3 终审，有权否决一切 |

路由规则：**用最便宜的、真正能判的那一层；永远不让某一层去判它验不了的东西。**让 LLM 判官去验「cron 装上服务器没有」是装饰 —— 它看不见服务器。让确定性脚本去判「摘要是否忠实原文」是噪声。

## 2. 判据必须可验证 —— mutation test

每条判据立之前先答四问，第四问承重：

1. 它断言的是什么，我真正在意的是什么，差在哪？
2. 被断言的为假时，它**响**还是静默放行？
3. 判据自己腐烂时（世界变了、清单没跟上），有人会知道吗？
4. **把被检的东西故意弄坏，判据会不会变红 —— 真验过一次吗？**

这是把 mutation testing 用到评估上。从没被证明会变红的判据不是门，是希望。我的 harness 里，门的改动必须附验证记录：造坏的 case、预期的红、实测的红。

## 3. 案例：降级判官放走两个真缺陷那天

教我最多的一次事故（2026-10-21，全程有记录）：

一张任务卡的终审跑在**降级判官档**上（主模型通路挂了，系统自动 fallback）。降级档给出 PASS。两个真缺陷溜了过去：

1. `check_results` 用 `== (2, 0, 0)` 比较统计元组 —— 但 Python 里 `2.0 == 2`、`False == 0` 都为真，浮点/布尔计数可以冒充绿色结果。
2. 报告文件缺失被报成「读不到文件」—— 把 eval **崩溃**掩盖成文件问题。

两个都是主通路恢复后**用真档重跑**才抓到的。修复新增了判据 16：两个判别性反例必须红 + 崩溃与不可读分离。

三条可泛化教训：

- **降级判定器的 PASS 只能当「先过、别停」，不能当收口依据。**降级环境下产出的任何评估必须带出具方标签。质量可降，诚实不可降。
- **退出码不是证据。**（同一次事故：eval runner 失败退出码是 100 —— 与 worker 崩溃同码。从此只解析结果 payload，不看退出码。）
- **逃逸是唯一重要的判据来源。**每个漏放缺陷变成一条新 golden case + 一条新判据。评估集从失败里长出来，不是事前设计出来的。

## 4. 判官独立性与 replay

LLM 判官有一种特定失败方式：它和产出被审物的模型**共享盲区**。缓解手段，全部实战检验过：

- **异族。**判官不能是产出方的亲兄弟。我的执行档和判官档曾有一度收敛到同一模型族，被独立性探针抓住后重路由。
- **对自述失明。**判官只看产物（diff），不看产出方的自我辩解。自报不算证据（与 doc 04 对账门同一原理，应用到判断上）。
- **replay 归因。**判词看着不对就带仪表重跑。一个看似「判官质量天花板」的 ceiling，最后是日志函数的 artifact —— 只有 replay 分得出来。

## 5. 让评估体系保持诚实的指标

- **逃逸率** —— PASS 之后才发现的缺陷。唯一北极星，其他都是代理。
- **每任务 rework 轮数** —— 上升趋势 = 判据不清或判官失准。
- **假完成率** —— 「成功」的运行里，下游产物不存在或过期。
- **判官一致/推翻率** —— 人审门推翻判官链的频率。太高：判官是噪声；太低：人审门在盖章。

警惕 Goodhart：指标变目标那天，harness 就开始为指标优化。指标用来知情，门用来决策。

## 6. 客户现场的头两周

1. **先写 competency questions。**在任何 rubric 之前：列出应用必须答对的 10–20 个问题（业务验收口径）。这就是 golden set 种子 —— 尽可能从**真实历史失败**里取。
2. **最小规模立起三层栈。**确定性校验管精确条件；一个校准过的、与产出方异族的 LLM 判官；高风险切片留人审门。
3. **逃逸环从第一天接线。**每个生产漏判 → 新 golden case + 新判据。每周过逃逸库，评估集复利增长。
4. **每个判词带出具方标签。**降级评估显式标注，收口必须全档判词。
5. **对前五大判据做 mutation test。**按每条判据声称能抓的方式故意弄坏输出。不变红，不算门。

## 7. 词汇对照

| 标准术语 | 我的对应实践 |
|---|---|
| Golden set / eval dataset | 34 条 golden set，从逃逸里长出来 |
| LLM-as-judge | 三层判官链，异族独立，定期校准 |
| Eval harness | 任务卡 → L0–L3 门流水线，metrics 回写 |
| Mutation testing（用于 eval） | 判据四问 + 每门验证记录 |
| 线上回归 / 漂移监控 | 新鲜度看门狗 + 每日路由健康探针 |
| Human-in-the-loop | 风险驱动终审门，不是逐步审批 |

## 边界

以上证据来自代码域 —— 那里 ground truth 便宜（测试能跑、schema 能对账）。方法论可迁移，但开放域（摘要、agent 对话、研究报告）的**校准成本**更高，面试里我会明说而不是夸大。承诺不变：任何 engagement 我建的第一件东西是逃逸库 —— 因为能守住应用的评估体系，是从它自己的失败里长出来的，从第一个失败开始。
