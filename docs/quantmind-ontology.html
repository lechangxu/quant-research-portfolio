为什么要有本体。2026-09-06 判例：两张因子表同时缺席四份独立维护的字面量清单，停更 42 天无人发现，182 个目录因子里 92 个静默消失。根治不是「多加几个检查」，而是把域建模成本体 —— 一张注册表作为唯一真源，所有清单、监控、目录、API 从它派生。

03 · ACTIONS动作 + 许可门

动作不是「函数」，是带前置条件、验证证据、失败路径的操作。

Action触发前置 gate完成证据（不接受自报）失败路径
daily-updatecron 07/12/20flock 防重入；launcher 统一入口manifest 原子写（含 max_trade_date）关键阶段 exit 1 → 不写 manifest → HK 停拉 → 告警
sync-to-hkcron 21:00manifest 新鲜校验原子换 DB + ActiveState=active 断言校验失败 → 保留旧快照，服务不中断
register-factor-table人工（开发）registry 登记（唯一入口）schema 对账（声明列 vs 实际列）对账失败 → 部署审计 --audit 红
backfill-*人工/补数容差内不得与 daily update 竞争写库行数 + freshness 复测退出 0 但写 0 行 = 假完成，freshness 次日抓
deploy人工 pushCI check_sql.py 绿verify_update_server.sh --audit 实弹红 → 回滚上一快照
ic-recomputecron / 随更新因子表新鲜（max_lag 内）IC 文件 mtime + 区间对账过期因子 → IC 标 degraded

A2 对账门 —— 永不接受进程自报的成功

systemctl restart 退 0 ≠ 服务在跑；backfill 退 0 ≠ 写了数据。每个 action 的「完成证据」列就是这条门的物化。

假完成（false-completion）是头号敌人

09-06 事故的本质不是「没人检查」，是四份清单各自以为对方在检查。本体化后，被巡检集合 ≡ 注册集合，恒等式成立 —— 「漏登记的新表逃出监控」这个失败模式从结构上不存在。

degraded 是一等公民

manifest 带 degraded 标志：允许带病交付，但病必须显式声明、随数据流到消费者，不许静默。

04 · GOVERNANCE本体自身的变更治理

  • 门的成文法：repo CLAUDE.md 的 A1–A7（判据四问 / 对账门 / 改动幅度门 / 契约门 / 有界门 / 启动前置门 / 元规则）是本体宪法。每条门带 Q4 验证记录 —— 把被检的东西弄坏，判据必须变红（业界叫 mutation testing）。
  • 注册表即 PR 对象：改 registry = 改本体，走 git review；test_registry.py 保证注册表自身一致性。
  • 派生恒等式有测试：check_arch_drift.py / check_claims.py 防止代码漂移出本体描述。
  • 跨机契约文件化：docs/architecture.md 与 crontab（install-cron.sh 幂等安装）互为对账。
  • 事故台账回流：每次本体失效都产生一条新 gate 或新属性（如 manifest 的 degraded），写回本体。本体是长出来的，不是设计出来的。
